# MiceHole 项目记忆与 MD 工作习惯

> 适用于 `main` 源码中 2026-10-16 起的轻量项目记忆改进。**ChatGPT 是唯一负责规划与判断的 AI；MiceHole 只是读写本机文件、运行程序和返回结果的执行工具。**

## 解决什么问题

长时间开发会跨越多个 ChatGPT 会话。仅靠聊天上下文可能忘记已完成的工作、验收证据或下一项任务。项目文档可以保存少量、可验证的事实，减少重复审计和重复施工。MiceHole 不增加独立 Agent、数据库、调度器或定时监控。

## 新会话：按需读取

1. 确定正确的项目目录；在需要时读取**当前工作区和项目**的 `AGENTS.md`（如果存在），不重复加载已知规则。
2. 续工优先通过 `mouse_hole_read` 读取 `construction://continue?project=projects%2Fdemo`，或读取该项目唯一的权威 `STATUS.md`。`construction://continue` 读取入口不会修改文件；需要主动恢复状态时再调用相应写入操作。
3. 需要架构信息再读设计文档；需要历史原因再查 LOG；选工具时才查看资产目录。不要因为文件存在就一次性读取全部。
4. 在宣称完成之前，用真实文件、Git、进程或测试结果核验。**MD 是项目记忆，不是验收证明。**

## 新项目：按规模初始化

| 情况 | 推荐做法 |
|---|---|
| 一次性脚本、小实验 | 不为形式额外创建 MD |
| 需要跨会话继续的一般项目 | 项目 `AGENTS.md`（本项目特例）和唯一 `STATUS.md`（目标、进度、证据、阻塞、下一动作）；已有同等文件就复用 |
| 大型长期工程 | 确有必要时再增加 `PROJECT.md`、`TODO.md`、`LOG.md` 或专题文档 |

MiceHole 的受管四文件记忆格式是**可选模型**，不是所有 Git 仓库或项目必须采用的约束。不要创建两个相互竞争的 STATUS。

## 何时写 MD

- **应该写：** 验证过的开发里程碑、重要方案决定、关键阻塞、正式验收、对下一次续工有影响的变化。
- **不需要写：** 每条命令、重复读取、纯状态检查、普通测试进程启动/等待、无变化的检查点。
- **如何写：** 优先更新唯一权威 STATUS；确实有独立历史价值才更新 LOG。保存实际结果、证据与下一条可执行动作。保留人工编辑及已有内容，不覆盖其他会话的变更。
- **安全：** 不把密钥、令牌、私人资料及完整终端输出复制到项目记忆中。

## 2026-10-16 修复：进程状态不污染项目记忆

此前，`mouse_hole_process.start/wait` 的执行进度可能自动持久化为 `WAITING_PROCESS` / `RUNNING`，并将项目下一步替换为含糊的 `wait_for_process` / `continue_plan`。现已把进程 ID、等待状态和退出结果保留在**连接内临时执行记录**，不再自动覆写 `PROJECT.md`、`STATUS.md`、`TODO.md`、`LOG.md`。

只有 ChatGPT 明确调用项目检查点/恢复/完成等接口时才改变持久状态。已有安全边界、人机授权和现有工具集合不变。

## 验证范围与局限

- 本仓库运行 `node scripts/test-md-habit.mjs`：验证分层规则发现、状态读取无副作用、无变化 checkpoint 幂等、进程状态源码边界和正式里程碑写入。
- `node scripts/test-direct-port.mjs`：验证公开 Direct 包 12 工具、握手和基本文件访问。
- 开发环境另已完成 11 套、122 项回归检查，且真实连接下的进程启动与等待测试未改变项目 MD 哈希。**这是开发环境证据，不是对每台公开版 Windows 电脑的兼容性承诺。**
- 公开独立包在没有配置可用进程后端时，`process.start` 可能报告 `execution_unknown`；不要盲目重试。真实进程端到端验收需在已明确授权并安装好执行后端的环境中进行。
- 一次受控对照实验表明，减少重复读取与写入能节省工具调用量，但**尚未证明 ChatGPT 的真实端到端开发速度提高了特定百分比**。

## 适用边界

本机制不自动注入外部 ChatGPT 会话的全部文件，也不能强制模型每次都完美遵循文档。它只让 ChatGPT 更容易定位正确的状态并安全地执行读写，不在本机再运行一个会替 ChatGPT 作决定的 AI。
